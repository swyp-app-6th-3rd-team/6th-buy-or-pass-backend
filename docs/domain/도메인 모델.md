# 도메인 모델

개발할 때 참고하는 지도다. 이 도메인이 무엇이고, 어떤 규칙으로 움직이는지를 담는다.
용어의 뜻은 [용어사전.md](./용어사전.md)에 있다.

## 이 서비스

**DVD 대여점의 대여와 반납을 관리한다.** 고객이 재고를 빌려 가고, 돌려주고, 늦으면 연체로 판정한다.

Sakila 샘플 데이터베이스를 기반으로 하되, 스키마를 그대로 옮기지 않고 대여라는 행위에 필요한 것만 도메인으로 세운다.

---

## 하위 도메인 분류

어디에 노력을 쏟을지 정하기 위한 분류다. 분류가 바뀌면 투자도 바뀐다.

| 하위 도메인 | 유형 | 근거 | 투자 |
|---|---|---|---|
| **대여**(rental) | 핵심 | 대여 기간 계산과 연체 판정이라는 규칙이 있다. CRUD 화면으로 환원되지 않는다. | 깊게. 규칙을 문서로 고정하고 도메인 테스트로 지킨다. |
| **인증**(auth) | 일반 | 소셜 로그인은 모든 서비스가 같은 방식으로 한다. 이 서비스를 차별화하지 않는다. | 얕게. 검증된 방식을 그대로 쓰고 규칙만 최소로 기록한다. |

> 분류는 고정이 아니다. 대여가 흔한 문제로 굳어지거나 인증에서 이 서비스만의 규칙이 자라면 다시 판정한다.

**여기서 더 쪼개지 않는 이유** — 대여를 더 나눠도 나온 조각이 모두 핵심으로 남고, 인증을 나눠도 모두 일반으로 남는다. 쪼개도 분류가 바뀌지 않으면 그만 쪼갠다.

## 핵심 개념과 관계

```
[rental 컨텍스트]                      [auth 컨텍스트]

  ◆ 대여 (Rental)                        ◆ 사용자 (User)
    · 재고 · 고객 · 직원                    · 소셜 신원 (제공자 + 제공자 식별자)
    · 대여일 → 반납일(없을 수 있음)          · 권한
    · 대여 기간 · 연체 판정                  · 활성 ⇄ 비활성 (단방향)

  대여 검색 조건 (RentalSearchCondition)

           ┊
           ┊ 고객과 사용자는 아직 이어져 있지 않다
           ┊
```

`◆` = 애그리거트 루트. 저장과 조회는 루트 단위로만 한다.

- **대여**는 재고·고객·직원을 식별자로만 안다. 그 실체를 자기 안에 두지 않는다.
- **연체 판정에 필요한 허용 일수를 대여가 갖고 있지 않다.** 바깥에서 받는다 — 허용 일수는 대여 건마다 정해지는 값이 아니라 정책이기 때문이다.
- **고객과 사용자는 연결돼 있지 않다.** 지금은 서로를 참조하지 않는다. 이어야 할 일이 생기면 그때 결정하고 ADR로 남긴다.

## 규칙

각 규칙에 ID를 붙인다. ID는 문서와 코드를 잇는 앵커다.

| ID | 규칙 | 컨텍스트 | 코드 | 테스트 |
|---|---|---|---|---|
| R-01 | 이미 반납된 대여는 다시 반납할 수 없다 | rental | `Rental.java:77` | `RentalTest.java:73` |
| R-02 | 반납일은 대여일보다 앞설 수 없다 | rental | `Rental.java:80` · `Rental.java:47` | `RentalTest.java:84` |
| R-03 | 연체는 반납되지 않았고 대여 기간이 허용 일수를 넘어선 것이다. 반납된 대여는 아무리 늦었어도 연체가 아니다 | rental | `Rental.isOverdue` | `RentalTest.java:135` · `RentalTest.java:144` |
| R-04 | 대여 기간은 반납 전이면 기준 시각까지, 반납 후면 반납일까지 센다 | rental | `Rental.rentedDays` | `RentalTest.java:117` · `RentalTest.java:125` |
| R-05 | 대여 검색 조건의 종료일은 시작일보다 앞설 수 없다 | rental | `RentalSearchCondition.java:18` | — |
| R-06 | 이미 탈퇴한 사용자는 다시 탈퇴할 수 없다 | auth | `User.java:66` | `UserTest.java:89` |
| R-07 | 사용자는 소셜 신원(제공자 + 제공자 식별자) **쌍**으로 식별한다. 제공자 식별자만으로 찾으면 제공자가 다른 서로 다른 사람이 한 계정으로 합쳐진다 | auth | `User.java:6-8` · DB 복합 유니크 제약 | — |
| R-08 | 프로필 동기화에서 빈 값이 오면 기존 값을 지우지 않는다 | auth | `User.java:56-61` | `UserTest.java:60` |
| R-09 | 새 사용자는 활성 상태·일반 사용자 권한으로 시작한다 | auth | `User.java:25` | `UserTest.java:18` |

**빈 칸이 뜻하는 것**
- `코드` 열이 비면 아직 구현되지 않은 규칙이다.
- `테스트` 열이 비면 규칙은 있으나 회귀를 막을 장치가 없다. R-05·R-07이 지금 그렇다.
- 이 표에 없는데 도메인 코드에서 예외를 던지는 곳이 있으면, 규칙인데 적히지 않은 것이거나 규칙이 아닌 방어 검증이다.

### 규칙이 아닌 것

아래는 코드에서 예외를 던지지만 도메인 규칙이 아니라 **입력 방어**다. 규칙 표에 올리지 않는다.

- 식별자(재고·고객·직원)가 양수여야 한다 — `Rental.java:35,38,41`
- 대여일이 있어야 한다 — `Rental.java:44`
- 반납 시각이 있어야 한다 — `Rental.java:74`
- 제공자·제공자 식별자가 있어야 한다 — `User.java:31,34`

이것들을 규칙으로 올리면 표가 방어 코드로 뒤덮여 진짜 규칙이 묻힌다.

## 상태와 전이

### 대여

반납일의 유무가 곧 상태다. 별도의 상태 값을 두지 않는다.

```
[대여 중] ──returnAt()──▶ [반납됨]
   │                      │
   └── 연체 판정 대상        └── 연체가 될 수 없다 (R-03)
```

되돌아가는 전이는 없다. 반납을 취소하는 개념이 이 도메인에 아직 없다.

### 사용자

```
[활성 ACTIVE] ──withdraw()──▶ [비활성 INACTIVE]
```

**단방향이다. 비활성에서 활성으로 돌아오는 경로가 코드에 없다.**

이것은 관찰된 사실이며, 다음 질문에는 아직 답이 없다:

- 탈퇴한 사람이 같은 소셜 신원으로 다시 오면 어떻게 되는가? 기존 사용자를 되살리는가, 새 사용자를 만드는가?
- R-07이 소셜 신원 쌍에 유니크 제약을 걸었으므로 **새 사용자를 만드는 길은 지금 막혀 있다.** 즉 현재 코드에서 탈퇴자는 재가입할 수 없다.

이 결정이 의도된 것인지 확인이 필요하다. 확정되면 규칙 표에 올리고 ADR로 남긴다.

## 다루지 않는 것

의도적으로 이 모델에서 뺐다. 뺐다는 사실 자체를 기록해 둔다.

| 뺀 것 | 이유 |
|---|---|
| 로그인·로그아웃 절차 | 모든 서비스에 있는 일반 기능이다. 이 도메인을 설명하지 않는다. |
| 연체료 계산 | 아직 요구되지 않았다. 필요해지면 R-03 옆에 규칙으로 추가한다. |
| 재고·작품의 상세 구조 | 대여가 식별자로만 참조한다. 대여 도메인의 관심사가 아니다. |
| 결제 | 이 서비스 범위 밖이다. |
| 사용자 권한 체계의 확장 | 지금은 일반 사용자 하나로 충분하다. |

## 이 문서를 유지하는 방법

- **규칙을 발견한 시점에 표에 쓴다.** 구현을 끝낸 뒤 몰아서 쓰면 왜 그렇게 정했는지가 사라진다.
- **코드에서 문서로 오는 방향이 더 자주 일어난다.** 구현하다 규칙을 발견하면 표를 갱신한다. 문서를 먼저 쓰고 코드를 맞추는 경우만 있는 게 아니다.
- **용어가 바뀌면 코드의 이름도 바꾼다.** 용어 변경은 모델 변경이다.
- 완료를 선언하기 전 이 표와 코드를 대조한다. 표에 있는데 코드에 없는 규칙, 코드에 있는데 표에 없는 규칙을 찾는다.
