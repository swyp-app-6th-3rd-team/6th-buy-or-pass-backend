# PRD-003 — OAuth2 + JWT 인증

**상태**: 완료

## 무엇을 왜

소셜 로그인부터 토큰 재발급까지 **실제로 도는 상태**로 만든다.
프로바이더 클라이언트 값만 채우면 바로 쓸 수 있어야 한다.

널리 쓰이는 Boot 3 예제는 Security 6.x 기반이라 그대로 옮기면 컴파일되지 않고,
동작은 해도 보안상 위험한 형태가 섞여 있다. **표준 구조를 따르되 알려진 결함은 미리 막는다**
([ADR-0006](../adr/0006-auth-hardening.md)).

## 범위

**포함**
- 소셜 로그인 3사 — Google · Kakao · Naver
- JWT 액세스·리프레시 발급/검증, 회전, 재사용 탐지
- Spring Security 7 설정 — `PathPatternRequestMatcher`, EntryPoint/AccessDeniedHandler
- `@CurrentUser` 파라미터 주입

**제외**
- Apple 로그인 — `id_token` JWKS 검증·`.p8` EC 키·ES256 재서명이 필요해 템플릿에 과하다
- 액세스 토큰 즉시 무효화 — 블랙리스트(Redis 등)가 필요. 측정 없이 미들웨어를 들이지 않는다
- 권한 세분화 — `ROLE_USER`/`ROLE_ADMIN` 두 개만

## 완료 판정

| # | 판정 | 검증 방법 | 결과 |
|---|---|---|---|
| 1 | 인증 없이 보호 API 는 401 + JSON 이다 | 통합 테스트 + 실 HTTP 호출 | ✅ `ApiResponse` 형식 |
| 2 | 브라우저 Basic 인증 팝업이 뜨지 않는다 | `WWW-Authenticate` 헤더 부재 확인 | ✅ 없음 |
| 3 | 액세스 토큰으로 내 정보를 읽는다 | `/api/auth/me` 200 | ✅ |
| 4 | 리프레시 토큰이 URL 에 노출되지 않는다 | 성공 핸들러 코드 + 응답 본문 검사 | ✅ 쿠키 단일 경로 |
| 5 | 리프레시 토큰이 해시로 저장된다 | 저장 호출 인자가 `hash(token)` 인지 검증 | ✅ SHA-256 |
| 6 | 재발급 시 토큰이 회전된다 | 재발급 후 쿠키 값 비교 | ✅ 다른 값 |
| 7 | 회전된 옛 토큰은 거부된다 | 옛 토큰으로 재발급 시도 | ✅ 401 |
| 8 | 해시 불일치 시 저장 토큰을 폐기한다 | `deleteByUserId` 호출 검증 | ✅ |
| 9 | 액세스↔리프레시를 바꿔 쓸 수 없다 | `typ` 클레임 검증 | ✅ 양방향 차단 |
| 10 | 만료 토큰은 EXPIRED_TOKEN 이다 | 시계를 31분 앞으로 | ✅ |
| 11 | 서명 위조 토큰은 INVALID_TOKEN 이다 | 서명부 변조 | ✅ |
| 12 | 프로바이더가 달라도 providerId 충돌이 없다 | 같은 providerId 로 두 프로바이더 삽입 | ✅ 별개 사용자 |
| 13 | 같은 계정 재로그인 시 사용자가 늘지 않는다 | 두 번째 로그인 후 ID 비교 | ✅ 동일 ID + 프로필 갱신 |
| 14 | 32바이트 미만 키는 기동을 막는다 | 짧은 키로 `AuthProperties.Jwt` 생성 | ✅ `IllegalStateException` |
| 15 | 3사 응답 구조 차이를 흡수한다 | 평평/중첩/래퍼 구조 파싱 | ✅ 6건 |

## 발견한 문제

| 문제 | 원인 | 조치 |
|---|---|---|
| `Client id of registration 'google' must not be empty` | 미설정 프로바이더가 기동을 막음 | 자리표시자 기본값. 실제 값이 없으면 해당 로그인만 실패 |
| `ObjectMapper` 빈 없음 | Boot 4 는 Jackson 3(`tools.jackson`) | import 경로 변경 |
| `PathPatternRequestMatcher` 심볼 없음 | 패키지가 `...web.servlet.util.matcher` | import 수정 |
