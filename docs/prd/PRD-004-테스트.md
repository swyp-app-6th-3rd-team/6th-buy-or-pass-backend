# PRD-004 — 테스트와 아키텍처 규칙

**상태**: 완료

## 무엇을 왜

템플릿의 가치는 "구조가 유지되는 것"이다. 문서로만 남은 규율은 지켜지지 않으므로
**아키텍처 규칙을 테스트로 강제**한다.

또 비즈니스 로직(대여·반납 규칙, 토큰 회전, 동적 조회, keyset 스크롤)이 실재하므로
계층별로 테스트를 둔다. 빌드 green 은 대리지표이므로 그것만으로 완료를 선언하지 않는다.

## 범위

**포함**
- 도메인 단위 테스트 — 컨테이너·스프링 컨텍스트 불필요
- 서비스 단위 테스트 — Store 를 mock 으로, `Clock` 고정
- 통합 테스트 — TestContainers MySQL, 실제 QueryDSL·스크롤·인증 플로우
- ArchUnit 아키텍처 규칙

**제외**
- 부하 테스트 — 측정 목표가 정해지지 않았다
- E2E (실제 소셜 프로바이더 왕복) — 외부 시스템 의존

## 규칙 검증 — 위반 주입

**통과만으로는 규칙이 무언가를 지킨다는 증거가 되지 않는다.** 5가지 위반을 주입해
해당 규칙만 실패하는지 확인했다.

| 주입한 위반 | 실패한 규칙 | 다른 규칙 |
|---|---|---|
| 도메인에 `@Entity` | 도메인은 JPA 에 의존하지 않는다 | 17건 통과 |
| 도메인에 `@Getter` | 도메인은 롬복을 쓰지 않는다 | 나머지 통과 |
| 컨트롤러가 `Page` 반환 | 컨트롤러는 Page 를 그대로 응답하지 않는다 | 나머지 통과 |
| 서비스가 `FilmRepository` 주입 | 서비스는 리포지토리에 직접 의존하지 않는다 | 나머지 통과 |
| `sakila` 가 `Rental` 참조 | Sakila 예제는 DDD 참조 구현을 침범하지 않는다 | 나머지 통과 |

**이 과정에서 규칙 하나의 버그를 찾았다.** "컨트롤러는 엔티티를 노출하지 않는다"가
이름만으로 필터링해 Spring 의 `ResponseEntity` 까지 잡고 있었다(JPA 엔티티가 아닌데도).
패키지 조건을 추가해 고쳤다. 만약 컨트롤러가 `ResponseEntity` 를 쓰지 않았다면
**규칙은 초록색인데 정작 엔티티 유출은 못 막는** 상태로 남았을 것이다.
