# PRD-005 — 관측성

## 무엇을 왜

이 템플릿은 "무슨 일이 났나"(로그)와 "살아있나"(health)만 답할 수 있었다.
**"시간이 어디서 샜나"** 를 답할 수단이 없었다.

특히 `application.yml` 의 `default_batch_fetch_size: 100` 은 처음부터 있었지만
**실제로 듣는지 검증한 적이 없었다.** 확인 수단이 `show-sql` 로그를 눈으로 세는 것뿐이었다.
관측성 도입의 목적 중 하나가 정확히 이 검증이다.

## 범위

### 포함

- OTel Java Agent 부착 (옵트인)
- 백엔드 독립 스택 — Collector / Tempo / Prometheus / Loki / Grafana
- Micrometer Prometheus 레지스트리 + 관리 포트 분리
- 로그에 `trace_id` · `span_id` 주입 (파일 로깅은 유지)
- JFR 상시 녹화 (`maxage=6h`)
- Grafana datasource · 대시보드 provisioning
- N+1 방어 검증 테스트

### 제외 (사유 포함)

| 제외 | 사유 |
|---|---|
| Pyroscope | JFR 로 충분한지 먼저 확인한다. 측정 없이 미들웨어 도입 금지 |
| Tail sampling | 단일 노드에 과하고 로그 게이팅과 충돌한다 |
| TurboFilter 샘플링 게이팅 | **[추정]** 공개 구현체가 없는 조합. 스파이크 대상 |
| SQL 바인드 값을 스팬에 담기 | sanitization 을 통째로 끄므로 운영에서 위험. 로거로 이미 확보됨 |
| 파일 로그의 JSON 전환 | 커스텀 `logback-spring.xml` 이 자체 appender 를 정의하므로 Boot 프로퍼티만으로는 안 된다. OTLP 경로가 별도로 있어 실익이 없다 |

## 완료 판정

**대리지표로 완료를 선언하지 않는다** — 컨테이너 Up · Grafana 접속 · 에이전트 기동 로그 ·
빌드 성공은 실패 판정용으로만 쓴다.

| # | 판정 기준 | 결과 |
|---|---|---|
| 1 | 스팬에 `db.statement` 가 담긴다 (SQL 계측) | ☑ `tracer: io.opentelemetry.jdbc` CLIENT 스팬 확인 |
| 2 | N+1 방어가 쿼리 횟수로 검증된다 | ☑ **30 회 → 1 회** (배치 끔 → 현재 설정) |
| 3 | Hikari 풀 지표가 노출된다 | ☑ `hikaricp_connections_{active,idle,max,pending}` |
| 4 | 액티브 요청 히스토그램이 1s/3s/5s 버킷으로 나온다 | ☑ `le=1.0/3.0/5.0` 확인 |
| 5 | 로그에 `correlationId` 와 `trace_id` 가 함께 찍힌다 | ☑ `CorrelationIdLoggingTest` 가 두 값이 **같은 로그 이벤트**에 담기는지 검증. 에이전트가 `trace_id` 를 실제로 채우는 것은 컨테이너 로그로 확인 |

| 7 | 에이전트 오버헤드가 절대값으로 기록된다 | ☑ p50 2.06→2.20ms, p95 2.50→3.14ms (표본 200) |
| 8 | 기존 테스트가 통과하고 옵트인이 지켜진다 | ☑ **113 건 통과**, 기본 실행 경로 불변 |
| 9 | 메트릭이 외부에 노출되지 않는다 | ☑ 관리포트 200 / 서비스포트 401 |
| 10 | 에이전트 jar 부재 시에도 앱이 뜬다 | ☑ 진입점 가드가 `-javaagent` 를 떼고 경고 후 기동 |

### 판정 5 의 증거 범위 (정확히 적는다)

독립 검증에서 **"실제 HTTP 요청 처리 중 두 ID 가 동시에 찍힌 로그 줄"** 이 확보되지
않았다는 지적을 받았고, 그 지적이 옳았다. 처음 확인했던 줄들은 `DispatcherServlet`
초기화 등 **`CorrelationIdFilter` 를 거치기 전의 기동 로그**라 `correlationId` 가 비어 있었다.

보강한 내용:
- `CorrelationIdLoggingTest.carriesCorrelationIdAndTraceIdTogether` 가
  필터 체인 안에서 로깅해 **두 값이 같은 `ILoggingEvent` 의 MDC 에 담기는지** 검증한다
- 에이전트가 `trace_id` 를 실제로 MDC 에 넣는다는 것은 컨테이너 로그에서 별도 확인했다
  (`[76f7ba1344317e699207d9c5087697e8]`)

**남은 한계**: 두 증거가 분리돼 있다. 에이전트가 붙은 상태에서 인증된 요청이
애플리케이션 로그를 남기는 시나리오를 아직 만들지 못했다 — 현재 공개 엔드포인트는
INFO 레벨 로그를 남기지 않고, 보호된 엔드포인트는 401 로 끊긴다.

측정 상세: [`docs/research/otel-measurements.md`](../research/otel-measurements.md)

## 진행 중 발견한 것

### Pinpoint 에서 방향 전환 (경위)

이 작업은 **Pinpoint APM 도입으로 시작**했다. 에이전트 계측 검증은 통과했으나
`pinpoint-hbase` 가 **amd64 단일 아키텍처**라 Apple Silicon 홈서버에서 기동하지 못했다.
4 회 시도 전부 실패. HBase 는 Pinpoint 3.x 에서 대체 불가다.

기각 근거와 조사 기록은 [ADR-0010](../adr/0010-observability-opentelemetry.md) 과
[`docs/research/`](../research/) 에 있다. Pinpoint 산출물은 커밋 `4ee634a` 에 보존했다.

### 계획을 바꾼 실측 3 건

1. **`rental` 슬라이스로는 N+1 을 만들 수 없다** — `RentalEntity` 의 FK 가 전부 스칼라라
   JPA 연관관계가 0 개다. `sakila` 패키지의 `Payment → Customer` 로 대상을 바꿨다.
2. **`Film → Language` 도 부적합하다** — Sakila 의 언어가 6 개뿐이라 1 차 캐시가
   부모 조회를 중복 제거해 N+1 이 드러나지 않는다.
3. **관리 포트 분리만으로는 401 이 난다** — Spring Security 필터 체인이 관리 포트에도
   적용된다. `EndpointRequest.toAnyEndpoint()` 를 매칭하는 전용 체인이 필요했다.

### 부수 수정

`README` 의 `docker compose up -d` 안내가 `-f` 없이 적혀 있어 **현재도 동작하지 않았다**
(`docker-compose.yml` 이 없고 `-dev`/`-prod` 만 존재). 이번 작업과 무관한 기존 결함이라
함께 고쳤다.

## 열린 질문

- **TurboFilter 샘플링 게이팅** — 샘플링된 요청만 바인드 값을 로깅하는 조합.
  API 는 각각 문서화돼 있으나 합친 공개 구현체가 없어 스파이크가 필요하다.
  ([`sampled-sql-bind-capture.md`](../research/sampled-sql-bind-capture.md))
- **부하 상태의 오버헤드** — 순차 요청 200 건으로만 측정했다. 동시 요청 다수에서의
  오버헤드는 미측정이다.
- **Loki 수집 경로** — 현재 OTLP 로만 보낸다. 파일 로그를 함께 수집하려면
  `info.log` 가 ERROR·WARN 을 포함하는 상위집합이라 3 중 수집을 피할 설정이 필요하다.
