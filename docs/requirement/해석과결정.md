# 해석과 결정

요구사항이 모호했던 지점과 확정 결과.

## 1. "Sakila 전체 Entity" × "DDD 차용" 의 충돌

요구사항 6(Sakila 16개 테이블 Entity)과 7(DDD 차용)은 서로 잡아당긴다.
16개를 전부 풀 DDD(도메인 모델 + 엔티티 + 매퍼 + Store)로 만들면 클래스가 60개를 넘어
**템플릿이 아니라 Sakila 애플리케이션**이 된다. 새 프로젝트를 시작할 때 지우는 데만 한참 걸린다.

**확정: "골격 + 참조 구현 1개"**

- `rental` 애그리거트 1개만 풀 DDD 로 시연
- 나머지 15개 테이블은 얇은 JPA 엔티티 + Spring Data 리포지토리
- 근거: [ADR-0001](../adr/0001-skeleton-plus-one-reference.md)

## 2. 인증 구현 범위

Spring Boot 4 / Security 7 은 이전 세대와 API 가 다르다.
`MvcRequestMatcher`·`AntPathRequestMatcher` 가 제거됐고, Jackson 이 3.x 로 바뀌었으며,
자동설정이 모듈별로 분리됐다. 기존 Boot 3 예제를 그대로 옮기면 컴파일되지 않는다.

**확정: Boot 4 기준으로 새로 작성하되, 흔한 보안 결함을 미리 막는다**

- 리프레시 토큰은 해시 저장 + 쿠키 단일 경로 + 회전 + 재사용 탐지
- `(provider, providerId)` 복합 유니크로 계정 혼선 방지
- `AuthenticationEntryPoint`/`AccessDeniedHandler` 구현 (401/403 을 JSON 으로)
- 리다이렉트 URI 화이트리스트 (오픈 리다이렉트 방지)
- 상세: [ADR-0006](../adr/0006-auth-hardening.md)

## 3. 프로바이더 선택

Apple 은 `id_token` JWKS 검증·`.p8` EC 키·ES256 client secret 5분마다 재서명이 필요해
템플릿에 과하다.

**확정: Google · Kakao · Naver**

세 곳의 응답 구조가 서로 달라(평평 / 중첩 / 래퍼) `OAuth2UserInfo` 추상화의 가치가 드러난다.

## 4. 빌드·모듈 구조

**확정: Gradle Groovy DSL · 단일 모듈**

멀티모듈은 의존 방향을 컴파일 타임에 강제하지만 QueryDSL APT 설정이 모듈별로 까다로워진다.
단일 모듈 + ArchUnit 으로 같은 목적을 달성하고, 필요해지면 그때 쪼갠다.

## 5. 스키마 관리

**확정: Flyway + `ddl-auto=validate`**

`validate` 는 엔티티와 실제 스키마가 어긋나면 기동 시점에 잡는다.
Sakila 엔티티 16개를 손으로 만드는 작업에서 이게 안전망이 됐다 — 실제로 버그 2건을 잡았다
([SPEC.md 변경 이력](../SPEC.md) 참조).
