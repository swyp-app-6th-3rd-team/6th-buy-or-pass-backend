# ADR-0003 — 시간은 LocalDateTime 으로 다루고 Clock 을 초 단위로 끊는다

**상태**: Accepted

## 맥락

두 가지 문제가 순서대로 드러났다.

### 1) `Instant` vs `LocalDateTime`

처음에는 엔티티의 시간 필드를 `Instant` 로 잡았다. 그런데 Sakila 의 시간 컬럼은 전부
`DATETIME` 이다 — **타임존 정보가 없다.**

`Instant` 는 UTC 기준 절대 시각이므로 JDBC 드라이버가 세션 타임존으로 변환을 시도한다.
그 결과 **서버 타임존 설정에 따라 읽는 값이 달라진다.** 온프레미스 홈서버에 배포할 계획이라
개발 장비(macOS)와 운영 장비(Linux)의 타임존이 다르면 조용히 어긋난다.

### 2) 정밀도 불일치 — 실측으로 발견

`LocalDateTime` 으로 바꾼 뒤에도 keyset 스크롤 통합 테스트에서 **3건 중 2건만** 조회되는
현상이 나왔다. 조사 결과:

```
rental.rental_date  →  datetime_precision = 0   (초 단위)
LocalDateTime.now() →  나노초 정밀도
```

인과:

1. `09:00:00.123456789` 로 저장 → DB 에는 `09:00:00` 으로 잘림
2. 커서는 영속성 컨텍스트에 남은 **잘리기 전 값**(`.123456789`)으로 생성
3. 다음 조각 조건: `rentalDate > 09:00:00.123456789 OR (= AND id > 76)`
4. DB 의 세 번째 행은 `09:00:00` 이라 **두 조건 모두 거짓** → 조용히 누락

에러도 경고도 없이 데이터가 사라진다. 단위 테스트로는 잡히지 않았고,
실제 DB 를 왕복시킨 통합 테스트가 드러냈다.

## 결정

1. **모든 시간 필드는 `LocalDateTime`** 으로 다룬다. `Instant` 를 쓰지 않는다.
2. **`Clock` 빈을 초 단위로 끊는다.**

```java
@Bean
public Clock clock() {
    return Clock.tick(Clock.system(ZoneId.of("Asia/Seoul")), Duration.ofSeconds(1));
}
```

애플리케이션이 만드는 시각의 정밀도를 **컬럼 정밀도에 맞춘다.** 컬럼을 `datetime(6)` 으로
올리는 대신 이쪽을 택한 이유는 Sakila 원본 스키마를 최대한 보존하기 위해서다.

3. 컨테이너와 JDBC 양쪽에 타임존을 고정한다 — `--default-time-zone=+09:00`,
   `hibernate.jdbc.time_zone: Asia/Seoul`.

## 결과

**얻은 것**
- 저장 직후 메모리의 객체와 DB 에서 다시 읽은 값이 **같다.** 이 성질이 깨지면
  keyset 페이징뿐 아니라 낙관적 락·감사 로그 비교 등 여러 곳에서 조용한 버그가 난다.
- 서버 타임존이 바뀌어도 읽는 값이 변하지 않는다.

**포기한 것**
- 초 미만 정밀도를 잃는다. 같은 초에 생성된 두 행의 순서는 시간으로 구분되지 않으므로
  **정렬 키에 PK 를 반드시 덧붙여야 한다**(이 템플릿의 keyset 구현이 그렇게 되어 있다).
- 다중 타임존 서비스로 확장하면 `LocalDateTime` 은 부족하다. 그때는 컬럼을
  `TIMESTAMP` 로 바꾸고 `Instant` 로 전환해야 한다 — 되돌리기 비싼 결정이라 여기 남긴다.

**주의**: 마이그레이션에서 `datetime(6)` 을 쓴다면 `ClockConfig` 도 함께 바꿔야 한다.
둘 중 하나만 바꾸면 같은 버그가 재현된다.

## 검토한 대안

| 대안 | 기각 사유 |
|---|---|
| `Instant` 유지 + 세션 타임존 고정 | 설정 하나에 정합성이 걸린다. 운영 장비에서 누가 바꾸면 조용히 깨진다 |
| 컬럼을 `datetime(6)` 으로 변경 | Sakila 원본 스키마를 더 크게 손대야 하고, 기존 Sakila 덤프와 호환이 어긋난다 |
| 커서 생성 시에만 값을 자른다 | 증상만 막는다. 저장 직후 객체와 DB 값이 다른 근본 문제는 남아 다른 곳에서 재발한다 |
| `LocalDateTime.now().truncatedTo(SECONDS)` 를 호출부마다 | 호출부가 늘 때마다 빠뜨릴 수 있다. `Clock` 한 곳에서 보장하는 편이 안전하다 |
