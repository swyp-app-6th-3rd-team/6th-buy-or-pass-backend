# ADR-0001 — 골격 + 참조 구현 1개

**상태**: Accepted

## 맥락

요구사항이 두 가지를 동시에 요구했다.

- Sakila 16개 테이블의 JPA Entity 와 Repository
- DDD 차용 (도메인 모델과 엔티티 분리, Store 인터페이스를 도메인에)

두 요구가 서로 잡아당긴다. 16개를 전부 풀 DDD 로 만들면 테이블당 최소 4개 클래스
(도메인 · 엔티티 · Store 인터페이스 · Store 구현) 가 필요해 **64개를 넘는다.**

그러면 이건 템플릿이 아니라 Sakila 애플리케이션이다. 템플릿의 가치는
"새 프로젝트를 빨리 시작하게 해주는 것"인데, 시작하자마자 60개 클래스를 지워야 한다면
가치가 사라진다.

반대로 16개를 전부 얇은 엔티티로만 두면 DDD 를 시연하지 못해 요구사항 8이 빈다.

## 결정

**골격 + 참조 구현 1개**로 나눈다.

| 대상 | 방식 | 클래스 수 |
|---|---|---|
| `rental` 애그리거트 | 풀 DDD — 순수 도메인 · 엔티티 · Store 인터페이스/구현 · QueryDSL · 컨트롤러 | 9 |
| 나머지 15개 테이블 | 얇은 `@Entity` + `JpaRepository` | 30 |

`rental` 을 고른 이유는 **상태 전이가 실재하기 때문**이다 — 대여 → 반납은 되돌릴 수 없고,
이미 반납된 건을 다시 반납하면 안 된다. 이런 규칙이 있어야 "도메인 모델이 왜 필요한가"가
설명된다. `actor`(id, 이름 두 개)로는 시연할 게 없다.

패키지도 경계를 나눈다. `sakila` 패키지는 통째로 지울 예제이고, `rental` 은 남길 참조 구현이다.
ArchUnit 규칙으로 `sakila → rental` 의존을 금지해 **예제를 지울 때 참조 구현이 깨지지 않게** 한다.

## 결과

**얻은 것**
- 새 프로젝트 시작 시 `sakila` 패키지만 지우면 된다.
- DDD 를 "설명"이 아니라 "돌아가는 코드"로 시연한다.
- 얇은 엔티티 15개가 스키마 커버리지를 유지하므로 Sakila 로 실습할 수 있다.

**포기한 것**
- 애그리거트 간 관계(예: Rental 과 Customer 의 경계)를 시연하지 못한다. 애그리거트가 하나뿐이라
  "애그리거트 경계를 어디에 긋는가"라는 DDD 의 핵심 질문이 드러나지 않는다.
- `rental` 과 `sakila` 가 스타일이 달라 처음 보면 혼란스러울 수 있다.
  README 와 패키지 주석으로 의도를 명시해 완화한다.

## 검토한 대안

| 대안 | 기각 사유 |
|---|---|
| 16개 전부 풀 DDD | 클래스 64개+. 템플릿이 아니라 Sakila 앱이 된다. 지우는 비용이 시작 비용을 넘는다 |
| 핵심 3~4개(Rental·Film·Customer·Payment) 풀 DDD | 애그리거트 경계는 시연되지만 클래스 40개. 여전히 "지울 게 많은 템플릿"이고, 경계 설정은 도메인마다 다르므로 예제가 오히려 오해를 부른다 |
| DDD 골격만, 예제 애그리거트 없음 | 가장 가볍지만 "이렇게 쓰면 된다"는 살아있는 예제가 없다. 문서로만 남은 규율은 지켜지지 않는다 |
