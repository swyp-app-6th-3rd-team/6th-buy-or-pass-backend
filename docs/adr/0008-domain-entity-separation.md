# ADR-0008 — 도메인 객체와 JPA 엔티티를 분리한다

**상태**: Accepted

## 맥락

JPA 엔티티에 비즈니스 규칙을 함께 담으면 편하다. 클래스가 절반이고 변환 코드도 없다.
그런데 JPA 는 객체를 만드는 방식이 특이하다 — **리플렉션으로 빈 객체를 만들고 필드를 채운다.**
생성자를 우회하므로 생성자에 넣은 검증이 실행되지 않는다.

기본 생성자 없이 `@Entity` 를 붙이면 기동과 저장은 성공하는데 **조회에서만** 실패한다
(`org.hibernate.InstantiationException: No default constructor for entity`).
빌드 green, 기동 정상이라 대리지표만 보면 문제가 보이지 않는다.

기본 생성자를 열면 이번엔 **불변식이 없는 객체가 존재할 수 있게 된다.**
대여 도메인이라면 "재고 없이 만들어진 대여", "대여일 없는 대여" 같은 것이다.

## 결정

**도메인 객체와 JPA 엔티티를 물리적으로 분리한다.**

| 계층 | 클래스 | 책임 |
|---|---|---|
| `rental.domain` | `Rental` | 불변식과 상태 전이 규칙. 프레임워크 의존 0 |
| `rental.infra` | `RentalEntity` | 테이블 한 행 표현. JPA 가 요구하는 것을 전부 받아들임 |

**변환 방향은 엔티티 → 도메인이다.** `RentalEntity.toDomain()` / `from(Rental)`.
반대로 하면 `domain → infra` 역참조가 되어 아키텍처 규칙을 위반한다.
별도 매퍼 클래스를 두지 않고 엔티티가 변환을 소유한다.

**도메인에 Lombok 을 쓰지 않는다.** JPA 기본 생성자와 같은 성격의 위협이다 —
`@Builder` 는 생성자 검증을 통째로 건너뛰고, `@NoArgsConstructor` 는 기본 생성자를 열고,
`@Setter` 는 반납된 대여를 바깥에서 되돌릴 수 있게 만든다.
반면 **인프라·서비스에서는 Lombok 을 쓴다** — `@RequiredArgsConstructor` 는 `final` 필드만
골라 생성자를 만들어 필드 주입을 구조적으로 막는다.

**복원 전용 경로를 둔다.** DB 에서 읽은 "이미 반납된 대여"를
"생성자로 만든 뒤 `returnAt()` 호출"로는 복원할 수 없다 — 반납 시각이 지금으로 덮인다.
저장된 상태를 그대로 주입하는 `Rental.restore(...)` 정적 팩터리로 분리해
일반 생성과 명확히 구분한다.

**저장소 인터페이스는 도메인에, 구현은 인프라에.** `RentalStore`(domain) ↔
`JpaRentalStore`(infra). 인프라가 도메인을 향하므로 의존이 역전된다.
`RentalRepository` 는 **package-private** 이라 컴파일러가 인프라 밖으로 나가는 것을 막는다 —
ArchUnit 이전의 1차 방어선이다.

## 결과

**얻은 것**
- 유효하지 않은 `Rental` 객체는 존재할 수 없다. 생성자가 불변식을 강제한다.
- 도메인 단위 테스트가 컨테이너도 스프링 컨텍스트도 없이 돈다(`RentalTest` 14건).
- 서비스 테스트에서 Store 를 mock 으로 갈아끼울 수 있다(`RentalServiceTest` 5건).

**포기한 것 (정직하게)**
- 클래스가 늘고 변환 코드가 생긴다. `rental` 하나에 9개 클래스다.
- 필드를 추가하면 **두 곳을 고쳐야 하고**, 한쪽만 고치는 실수가 가능하다.
- 이 비용을 받아들이는 근거는 대여에 **상태 전이 규칙이 실재하기 때문**이다.
  단순 조회용 테이블이었다면 분리하지 않았을 것이다 — 실제로 Sakila 나머지 15개는
  얇은 엔티티로만 뒀다([ADR-0001](0001-skeleton-plus-one-reference.md)).

**규칙을 검증한 방법**
ArchUnit 규칙 18개를 만든 뒤, **일부러 위반하는 코드를 주입해 해당 규칙만 실패하는지**
5가지 경로로 확인했다(도메인에 `@Entity` / 도메인에 Lombok / 컨트롤러가 `Page` 반환 /
서비스가 리포지토리 직접 의존 / sakila 가 rental 침범). 이 과정에서 규칙 하나의 버그를 찾았다 —
"컨트롤러는 엔티티를 노출하지 않는다"가 이름만으로 필터링해 Spring 의 `ResponseEntity` 까지
잡고 있었다. 패키지 조건을 추가해 고쳤다.

> 통과만으로는 규칙이 무언가를 지킨다는 증거가 되지 않는다.
> 테스트가 초록색인데 보호는 없는 상태가 가장 나쁘다.

## 검토한 대안

| 대안 | 기각 사유 |
|---|---|
| 도메인에 `@Entity` + `protected` 기본 생성자 | 널리 쓰이는 방식이지만 불변식 우회 경로가 열린다 |
| `@NoArgsConstructor(access = PRIVATE)` | Hibernate 는 리플렉션이라 접근 제어가 실효 없다. 가려질 뿐이다 |
| `record` 로 도메인 작성 | 불변이라 상태 전이를 표현할 수 없다. 대여는 식별자가 고정되고 상태만 바뀐다 |
| 매퍼 클래스를 따로 둔다 | 클래스가 하나 더 늘고, 변환 로직이 엔티티 필드 변경을 따라가지 못할 위험이 있다 |
