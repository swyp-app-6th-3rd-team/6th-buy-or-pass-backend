# Resolve Problem

도구를 많이 호출하는 대신, 실제 질문과 원인을 좁혀 가장 값싼 판별 증거를 얻는 문제 해결 절차다.

## 시작 조건

다음 중 하나일 때 사용한다.

- 재현되지만 원인이 밝혀지지 않은 버그
- 측정이 필요한 성능·정합성 문제
- 요구사항이 모호하거나 서로 충돌하는 문제
- API, 데이터베이스, 인증, 외부 시스템 등 여러 경계가 얽힌 문제
- 되돌리기 비싼 설계 결정을 비교해야 하는 문제

## 절차

1. **질문 고정**
   - 사용자가 실제로 원하는 관찰 가능한 결과를 한 문장으로 쓴다.
   - 요청과 현재 접근이 다르면 구현 전에 차이를 알린다.

2. **현재 상태 분리**
   - 확인된 사실, 그 사실에서 나온 추론, 아직 확인하지 않은 가정을 구분한다.
   - 저장소 루트, 브랜치, 변경 상태, 관련 설정과 실행 환경을 먼저 확인한다.

3. **해상도 진단**
   - 깊이: 표면 증상 아래의 수정 가능한 원인을 설명할 수 있는가?
   - 넓이: 전제와 대안 접근을 최소 두 방향에서 검토했는가?
   - 구조: 관련 컴포넌트와 신뢰 경계, 데이터 흐름은 무엇인가?
   - 시간: 최근 변경, 배포, 설정 차이처럼 움직이는 요인이 있는가?
   - 해당 없는 축은 빠르게 건너뛴다.

4. **가설과 판별 증거 설계**
   - 가장 가능성 높은 가설부터 적되 첫 가설에 고정하지 않는다.
   - 각 가설마다 참일 때 보여야 할 증거와 거짓일 때의 증거를 적는다.
   - 여러 가설을 가장 싸게 구분하는 로그, 심볼 탐색, 단위 테스트, 요청 재현, SQL `EXPLAIN`을 먼저 선택한다.

5. **인과관계 좁히기**
   - 왜 발생했는지 반복해서 물어 수정 가능한 원인까지 내려간다.
   - 성능은 `호출 횟수 × 호출당 비용`으로 분해하고, 제거했을 때 예상 효과를 먼저 계산한다.
   - 같은 도메인·API 의미를 보존할 수 있을 때만 애플리케이션 필터보다 소스 쿼리를 우선한다. 중복 호출, 루프 안 I/O 같은 높은 레버리지도 함께 확인한다.

6. **최소 실험**
   - 가장 불확실한 가정 하나를 작은 spike로 검증한다.
   - 한 번에 한 변수만 바꾸고 성공·실패 기준을 미리 정한다.
   - 임시 실험 코드는 제품 변경에 섞지 않는다.

7. **결론과 선택지**
   - 증거가 지지하는 원인, 반증된 가설, 남은 불확실성을 구분한다.
   - 해결책이 여러 개면 효과, 구현·운영 비용, 가역성, 실패 모드로 비교한다.
   - 새 기술이 필요하면 `AGENTS.md`의 기술 도입 게이트를 적용한다.

8. **원래 시나리오 검증**
   - 수정 권한이 있는 요청이면 최소 변경을 구현하고 관련 테스트부터 실행한다.
   - 단위 테스트나 빌드 결과만이 아니라 처음 고정한 사용자 시나리오를 다시 확인한다.
   - 실행하지 못한 검증과 환경 제약을 명시한다.

## 결과 보고

다음을 짧고 분명하게 전달한다.

- 결론 또는 가장 가능성 높은 원인
- 이를 뒷받침하는 직접 증거
- 수정했을 때 바뀐 동작과 검증 결과
- 남은 불확실성, 미검증 범위, 다음 판별 방법

도구 출력은 그대로 나열하지 말고 `증거 → 의미 → 다음 판단`으로 변환한다.

## 경계

- 특정 공급자 전용 도구, 고정 모델, 자동 에이전트 전환이 존재한다고 가정하지 않는다.
- 분석 요청만 받은 경우 코드를 수정하지 않는다.
- 광범위한 전체 탐색은 필요한 핀포인트 탐색이 실패했을 때만 한다.
- PRD, ADR, 브랜치, 커밋, PR을 문제 해결 절차 자체의 필수 산출물로 만들지 않는다.
- 실제 비밀값이나 개인정보를 증거로 출력하지 않는다.
